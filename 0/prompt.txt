# How OpenTSLM actually built its training data

Repo: `/private/tmp/claude-501/-Users-gaurav-Downloads-zurich-lates-temporal-ai-error404-ai/6f11fbbe-b41b-4ac6-96cf-af296c485bf7/scratchpad/OpenTSLM` (single squashed commit `2968f4b`, no history to mine).
I downloaded all four released datasets and re-derived the numbers. Artifacts are in `…/scratchpad/probe/` and `…/scratchpad/m4.zip`.

**The single most important structural fact: the repo contains no data-construction code at all.** Every loader under `src/opentslm/time_series_datasets/` is a *consumer* — it downloads a finished CSV from an ETH Zurich polybox personal share, `ast.literal_eval`s the series strings, and wraps them in a `datasets.Dataset`. The merge, the resampling, the windowing, the plot rendering, the GPT-4o calls, and every filtering decision happened offline in code that was never published. The paper says (line 150 of the text): *"To facilitate further research, we release all code, datasets, and models as open-source resources."* The datasets are downloadable; the code that made them is not.

**Licensing: there is none.** No polybox artifact carries a licence, card, or checksum. The repo's MIT licence covers code only. `ChengsenWang/TSQA`'s licence field on HF is empty. PTB-XL is separately downloaded from PhysioNet (`ecgqa_loader.py:27`) so its licence follows the user, not the release.

**TSQA is not theirs and is perfectly synthetic.** From the HF statistics endpoint: 4 tasks × 3 labels × 4,000 = 48,000 exactly (`Trend`/`Seasonality`/`Volatility`/`Outliers`; labels like `upward trend`, `fixed seasonal`, `sudden spike`), answer options (a)/(b)/(c) balanced at 16,000 each, series length 64–512, mean 240. **The only documented discard in the whole project** is ECG-QA's comparison questions, in `src/opentslm/time_series_datasets/ecg_qa/README.md:24-36`: 414,348 → 231,536, *"Removed: 108,233 / 33,526 / 41,053"*. The paper (§4.1) adds *"we excluded comparison questions, retaining 42/70 templates. This yielded 3,138 unique questions across 240k samples"* — I measure 42 templates ✓ but 3,378 unique question strings in train alone, and 231,543 rows, not 240k.

**The only sample-filtering code that exists anywhere** is in the *legacy* PAMAP2 loader, `pamap2/pamap2_cot_loader.py:58,106-126`:
```python
def load_pamap2_cot_splits(seed: int = 42, min_series_length: int = 50):
    ...
        if x_len &gt;= min_series_length and y_len &gt;= min_series_length and z_len &gt;= min_series_length:
            valid_indices.append(idx)
        else:
            excluded_count += 1
```
Nothing equivalent exists for HAR-CoT, Sleep-CoT, ECG-QA-CoT or M4.

**The only raw→sample preprocessing code in the repo** is `pamap2/PAMAP2Dataset.py` (for the dropped PAMAP2 path). It is worth reading because it is the one place they did windowing properly — `_make_windows` (lines 160-190) groups by `subject_id` first *"so no window can span subjects"*, resamples to 3 s bins, takes the modal activity, and **drops any window whose modal label covers &lt;50% of rows**. None of that discipline survived into HAR-CoT.

### Contradictions between the paper and the released files

- **Sleep-CoT sampling rate.** Table 4 says 100 Hz / 30 s. `sleepedf_cot_loader.py:74` asserts `len(parsed[0]) == 1500`, and I confirmed every sampled row has exactly 1500 points. 1500/30 s = **50 Hz**. SleepEDF Fpz-Cz is natively 100 Hz, so it was silently halved.
- **Sleep-CoT class count.** §4.1 states: *"Following prior work (Chow et al., 2024; Pouliou et al., 2025), Non-rapid eye movement (REM) stages 3 and 4 are merged, yielding five classes."* The released `label` column has **six**: `{W:4209, N2:2571, REM:1180, N1:513, N3:447, N4:374}`. The merge was never applied. The paper's own Table 6 and its "Answer Selection Strategy" list also show six.
- **The 80/10/10 claim.** §4.1: *"All datasets are split into 80/10/10 train/validation/test sets."* True for TSQA, M4, Sleep. False for HAR-CoT (80.1/10.2/9.6) and badly false for ECG-QA-CoT (68.9/13.5/17.8), which uses ECG-QA's official folds.
- **ECG-QA-CoT count.** Table 4 says 159,313 train; Table 7 sums to 159,306; the actual CSV has 159,313.

## 2. The HAR-CoT merge — the mechanics

**There is no merge code, and the provenance is destroyed.** `har_cot/har_cot_loader.py:23` is the entire public surface:

```python
HAR_COT_RELEASE_URL = "https://polybox.ethz.ch/index.php/s/kD74GnMYxn3HBEM/download"
```

I downloaded it (140 MB → three CSVs, 579 MB). **Complete column list, identical in all three splits:**

```
x_axis, y_axis, z_axis, label, prompt, rationale
```

No `source`, no `subject`, no `device`, no `body_position`, no `timestamp`, no `id`. You cannot tell whether a row came from DaLiAc or Shoaib, cannot group rows by subject, and therefore **cannot rebuild a subject-disjoint split even if you wanted to**. For someone assembling a corpus from heterogeneous sources, this is the mistake to not copy: keep a provenance column, always.

**What I could recover empirically:**

- **Rate reconciliation: real, and verified.** Every sampled row has exactly 128 points per axis. 128 / 2.56 s = **50 Hz exactly**. Source rates ranged from 20 Hz (Shoaib) to 100 Hz (PAMAP2, DaLiAc), so all eight were resampled onto a common grid. The resampling method is unrecorded.
- **Unit reconciliation: also real.** Per-window max|value| over a 2,013-row sample: min 6.50, median 14.31, p95 41.9, max 69.5. **Zero rows below 3.** Since sitting is 27.7% of the data and a stationary window in *g* would peak near 1.0, there are no g-unit rows — everything was converted to **m/s²**. Gravity is retained (stationary windows sit at ≈9.8), so no high-pass/gravity removal was applied.
- **Per-device calibration: none.** There is no calibration step anywhere. Their entire answer to device heterogeneity is deferred to load time, in `har_cot/HARCoTQADataset.py:113-121`:

```python
        # Normalize the data with better numerical stability
        means = series.mean(dim=1, keepdim=True)
        stds = series.std(dim=1, keepdim=True)
        
        # Handle zero or very small standard deviations
        min_std = 1e-6  # Increased from 1e-8 for better stability
        stds = torch.clamp(stds, min=min_std)
        
        series_norm = (series - means) / stds
```
and then, lines 143-147, the discarded scale is handed back to the LLM **as text**:
```python
            text_prompt = f"{time_series_label}, it has mean {mean:.4f} and std {std:.4f}:"
            prompts.append(TextTimeSeriesPrompt(text_prompt, time_series))
```
This is the genuinely transferable trick: **per-sample, per-channel z-score to make heterogeneous sources commensurable, then re-inject the mean and std as natural language so absolute scale is not lost.** The paper names it as a weakness in Limitations (*"our method of encoding time-series may not be optimal, as we rely on including the mean and standard deviation in accompanying texts to preserve the temporal scale"*) but it is the mechanism that lets eight incompatible corpora share one encoder.

- **Label vocabulary.** The paper: *"We retain only those activity classes present in all datasets."* Survivors (8): `biking, lying, running, sitting, standing, walking, walking_down, walking_up` (`HARCoTQADataset.get_labels()`). Casualties are unrecorded, but by inspection of the sources the intersection kills PAMAP2's rope jumping / vacuum cleaning / ironing / Nordic walking / ascending-descending distinctions beyond stairs, DOMINO's cooking/eating/working classes, HHAR's "stairs" (which is not split up/down in all sources), and RealWorld's jumping. The harmonisation map from source label names to these 8 strings is not published.
- **Class balance was not enforced.** sitting 27.7% vs biking 5.9% — a 4.7× imbalance carried straight through. A `BalancedBatchSampler` exists (`pamap2/BalancedBatchSampler.py`) and `curriculum_learning.py:995` warns it *"is better to use ... for stage3_cot if dataset is imbalanced"*, but `stage3_cot()` at line 1289 sets `sampler = None` and never passes it.
- **Deduplication: none.** MD5 over `x_axis+y_axis+z_axis`: 210 exact duplicate windows within train, and **138 windows appear verbatim in both train and test** (1.7% of the test set), 140 in train∩val, 140 in val∩test. Small, but it proves no dedup and no source-aware splitting.
- **The loader defends against a botched concatenation** — `har_cot_loader.py:112-119`:
```python
    # Filter out rows that are actually headers (where x_axis == 'x_axis')
    initial_size = len(df)
    df = df[df['x_axis'] != 'x_axis']
```
That guard only makes sense if the merge was a naive concatenation of per-dataset CSVs *including their header rows*. (The current release is clean — 0 such rows — so this was fixed upstream after the guard was written.)

## 3. Augmentation and synthetic data — the answer is none

I ran an exhaustive search across all 163 files. **Zero hits** for: `augment`/`augmentation`, `jitter`, `perturb`, `mixup`, `cutmix`, `cutout`, `warp`/`time warp`/`magnitude warp`/`dtw`, `tsaug`, `audiomentations`, `random_crop`/`crop`/`window slicing`, `flip`/`[::-1]`/`torch.roll`/`reverse`/`rotation`, segment permutation, `synthetic`/`sinusoid`/`np.sin`/`random walk`/`brownian`/`arima`/`gaussian process`, `add_noise`/`gaussian noise`, `StandardScaler`/`MinMaxScaler`. No augmentation dependency in `pyproject.toml` or `requirements.txt`. No notebooks.

The architecture makes on-the-fly augmentation structurally impossible: `time_series_datasets/QADataset.py:40-56` materialises every formatted sample **once** into a class-level list at first construction, and `__getitem__` (lines 138-139) is a bare list index. Every epoch sees byte-identical tensors. The only training `collate_fn` (`util.py:52-64`) does constant zero-padding and deterministic head-truncation to a patch multiple — no randomness. The only stochasticity touching data anywhere is `DataLoader(shuffle=...)` batch ordering.

**TSQA is synthetic but not theirs.** `TSQADataset.py:41` is `load_dataset("ChengsenWang/TSQA", split="train")` — a third-party HF dataset from the ChatTime authors. There is no generator in the repo and the paper does not describe how those series were made.

**The one synthetic generator** is `time_series_datasets/simulation/SimulationQADataset.py:46-85`, and it is i.i.d. Gaussian noise:
```python
                series = torch.tensor(np.random.randn(self.length), dtype=torch.float32)
```
`DATASET_SIZE = 200`, constant label `"This is a random pattern."`, and line 85 returns `dataset, dataset, dataset` — train == val == test. It is imported only by `scripts/get_memory_use.py` and `evaluation/memory/get_memory_use.py` for VRAM benchmarking. `curriculum_learning.py` never imports it. It is not training data.

Deterministic resampling exists but is dimensionality reduction, not augmentation: `[::5]` for PTB-XL 500 Hz → 100 Hz (`ECGQACoTQADataset.py:392-393`, `ECGQADataset.py:297`) and `[:, ::2]` for PAMAP2 (`PAMAP2AccQADataset.py:97-99`). Both are **naive decimation with no anti-aliasing filter**.

## 4. Curriculum and mixing — the paper's "Stage 1" is two stages, and nothing is mixed

The paper frames it as two stages (Stage 1 = TSQA + M4, Stage 2 = the three CoT sets). The code does not mix anything. `curriculum_learning.py:61-67`:

```python
CURRICULUM_STAGES = [
    "stage1_mcq",
    "stage2_captioning",
    "stage3_cot",
    "stage4_sleep_cot",
    "stage5_ecg_cot",
]
```

Five **strictly sequential** stages, one dataset each — `dataset_class=TSQADataset` (line 1245), `M4QADataset` (1270), `HARCoTQADataset` (1295), `SleepEDFCoTQADataset` (1321), `ECGQACoTQADataset` (1347). Each stage loads the previous stage's `best_model.pt` (`_load_previous_stage_model`, line 561) and trains to convergence on its own data with early stopping (patience 5).

- **Concatenated, interleaved or sampled? None of the above — sequential.** `_merge_data_loaders` (line 302) does build a `ConcatDataset(datasets)`, but every call site passes a single-element list. The multi-dataset path is dead code.
- **Reweighting: none.** No loss weights, no sampling temperature, no per-dataset scaling.
- **Replay: none.** Nothing from stage *n−1* is revisited at stage *n*. There is no mitigation for catastrophic forgetting, and no measurement of it — the reported numbers per dataset come from separately-published checkpoints (`OpenTSLM/{base}-{tsqa|m4|har|sleep|ecg}-{sp|flamingo}`), i.e. one checkpoint per stage, not one model that retains all five skills.
- **LoRA is off for stages 1–2** and enabled only from stage 3 (`curriculum_learning.py:1556`, `1591`: `stages_with_lora = ["stage3_cot", "stage4_sleep_cot", "stage5_ecg_cot"]`). So stage 1–2 trains the **encoder and projector only**, with the LLM frozen — that is the concrete sense in which stages 1–2 are "encoder warmup".

**What the encoder is supposed to learn, and the evidence:** TSQA teaches discrete pattern vocabulary (trend / seasonality / volatility / outliers — literally the four `Task` values), M4 teaches free-form description of arbitrary real-world shapes. The paper's only justification is a citation: *"Following (Chow et al., 2024), we adopt a two-stage curriculum."*

**There is no ablation. Anywhere.** Grepping the full paper text for `ablation` returns zero hits. No stage-skipping experiment, no TSQA-only vs M4-only, no from-scratch comparison. The curriculum is pure assertion inherited from prior work. The one thing resembling evidence points the other way: §4.6 shows that swapping the trained-from-scratch encoder for pretrained Chronos-2 lifts TSQA from 77.86% to 99.69% and Sleep-CoT from 49.33 to 64.57 F1 — i.e. **a pretrained TSFM beats their two-stage warmup**, which quietly undercuts the need for stages 1–2 at all.

## 5. Quality control on the rationales — there is none, and I can quantify what that cost

**No generation code, no filter, no rejection, no regeneration.** The only OpenAI-touching files in the repo are `evaluation/baseline/openai_pipeline.py`, `common_evaluator.py`, and friends — all for running GPT-4o as an *evaluation baseline* (at `temperature: 0.1`), not for generating data. There is no script that renders a plot, calls GPT-4o at temp 0.3 / seed 42, validates the response, or retries. Nothing checks length, format, terminator correctness, or early answer leakage.

**"Manually reviewed" is unquantified.** The full extent of the paper's claim (§A.2):

&gt; *"We carefully engineered the prompts and manually reviewed a subset of samples to ensure the generated rationales were consistent and sensible."*

No count, no reviewer identity, no criteria, no inter-rater statistic. The 5-cardiologist / 84-sample expert review in §4.5 is a different thing entirely — it grades **OpenTSLM's own outputs at inference**, not the GPT-4o training rationales.

The prompts do all the QC work, and they are preserved verbatim in a `prompt` column in every released row — genuinely the most reusable artifact here. Note the two load-bearing constraints, from the HAR prompt:

&gt; *"- Do **not** assume any answer at the beginning — analyze as if you do not yet know which class is correct.*
&gt; *- Do **not** mention either class label until the final sentence.*
&gt; *- Make sure that your last word is the answer. You MUST end your response with "Answer: sitting":"*

The correct label is written into the prompt, so **every rationale is a post-hoc justification of a known answer, not reasoning**. And the *rendered plot* is what GPT-4o saw — the paper's own Limitations concede this model *"perform[s] poorly on these plots alone."*

**Measured defect rates in the shipped training data (my analysis, `probe/an2.py`, `probe/ecg_an.py`, `probe/sleep_an.py`):**

| | HAR-CoT train (68,542) | ECG-QA-CoT train (159,313) | Sleep-CoT (9,294) | M4 captions (100,000) |
|---|---|---|---|---|
| No parseable `Answer:` terminator | 1 (0.001%) | **681 (0.427%)** | 4 (0.043%) | n/a |
| Terminator ≠ ground-truth label | **157 (0.229%)** | **2,536 (1.592%)** | 7 (0.075%) | n/a |
| Label leaked before final sentence | 511 (0.75%) | — | — | n/a |
| Exact duplicate text | 982 (1.43%) | 479 (0.30%) | 295 (3.17%) | 58 (0.12%) |
| Literal API error string as target | 0 | 0 | 0 | **706 (0.706%)** |

Three things stand out:

1. **Wrong answers were shipped as ground truth.** 2,536 ECG-QA training rationales and 157 HAR ones end with a label that disagrees with the `answer`/`label` column, despite the correct answer being *printed in the prompt*. A one-line regex would have caught all of them. On ECG-QA that is 1.6% label noise in the largest dataset in the paper.

2. **M4 shipped its own error messages as training targets.** 706 of 100,000 captions are literally:
   - `Error generating caption: Connection error.` (630)
   - `Error generating caption: Error code: 404` (75)
   - `Error generating caption: Request timed out.` (1)
   
   Concentrated in Quarterly (396/24,000) and Daily (253/4,227 — **6.0% of that file**). Nothing filtered them; a `len(caption) &lt; 120` check would have removed exactly these 706 rows and nothing else.

3. **99.3% of M4 captions describe the picture, not the series.** e.g. *"The time-series graph displays data points over a span of approximately 450 units on the x-axis, with values ranging from 4000 to 14000 on the y-axis…"* The CoT prompts explicitly forbid this (*"Do not refer back to the plot or to the act of visual analysis"*); the M4 caption prompt is one line — `Generate a detailed caption for the following time-series data:` — with no such guard. So the encoder-warmup stage trains the model to narrate a chart it cannot see.

**Two design flaws in the generation setup itself:**

- **Binary generation, N-way training.** Rationales were produced under a 2-way choice, but `HARCoTQADataset._get_pre_prompt` trains against a prompt listing **all eight** labels (`"Possible activity labels are: biking, lying, running, sitting, standing, walking, walking_down, walking_up."`). The reasoning depth baked into each rationale is calibrated to a 2-way decision it will never face at inference.
- **The distractor is not "the most dissimilar".** The paper says *"we selected the most dissimilar activity from a predefined mapping."* Recovering the actual pairs from the `prompt` column shows **uniform random sampling within the map**: sitting's five distractors appear 3,829 / 3,824 / 3,803 / 3,794 / 3,747 times. The map itself matches Appendix A.2.1 exactly; the selection rule in the paper is misdescribed.

## The five things worth copying, and the five worth avoiding

**Copy:**
1. **Per-sample, per-channel z-score + re-inject mean/std as text.** The mechanism that makes heterogeneous sources commensurable without a global scaler. For rail delay: normalise each window, then say *"this segment has mean delay 4.2 min and std 7.1 min"* in the prompt.
2. **Store the generation prompt in the dataset**, one column per row. It makes the recipe recoverable even if the generator is lost — the only reason I could audit their distractor selection at all.
3. **Answer-set narrowing to a binary choice** with a hand-written dissimilarity map. It forces genuine discrimination instead of pattern-matching. But generate under the *same* answer set you will train and evaluate under (see below).
4. **The `Answer: &lt;label&gt;` terminator convention.** It makes parsing trivial and makes format failures measurable — which is exactly how text-only baselines got 0% F1 (§A.4) and how I could measure their own defect rates.
5. **`PAMAP2Dataset._make_windows`** — group by subject so windows never span subjects, take the modal label, drop windows where the mode covers &lt;50%. They wrote this and then didn't use it. Use it.

**Avoid:**
1. **Dropping the provenance column.** HAR-CoT is permanently untraceable to its eight sources and permanently un-resplittable by subject. Carry `source`, `subject`/`station`, `device` and `timestamp` through to the final release.
2. **Random-splitting windows from a handful of entities.** Sleep-CoT is 9,294 windows from **6 recordings**, split stratified-by-label at load time — every test subject is in train. ECG-QA-CoT, which used official record-level folds, has exactly 0 id overlap. Same project, two policies, opposite outcomes. Split by line/route/station, never by window.
3. **Shipping generation without a validator.** 2,536 ECG rationales end in the wrong answer; 706 M4 captions are literal `Connection error.` strings. A ten-line filter — terminator parses, terminator == label, length in range, no error prefix — would have removed all of it.
4. **Letting the caption/rationale describe the rendering.** 99.3% of M4 captions talk about "the x-axis" and "the graph". If you generate from plots, forbid plot references in the prompt (as they correctly did for the CoT sets and forgot for M4).
5. **A sequential curriculum with no replay and no ablation.** Five stages, each initialised from the last, nothing revisited, no forgetting measured, no evidence any of it helps — and their own §4.6 shows a pretrained TSFM encoder beats the warmup stages it was supposed to replace. If you adopt a curriculum, run the stage-skipping ablation they didn't.</result>
