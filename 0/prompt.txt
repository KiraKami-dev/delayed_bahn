<result>The existing services model delay per stop and per train run, then combine arrival and departure forecasts into a connection probability. None of the tools I checked groups delays by line. The dataset is live: its last commit was about 40 minutes before I checked.

## 1. How existing services model it

- **bahnvorhersage.de (formerly TCP):** it predicts a probability distribution of arrival and departure delay for every stop of a train run ("for each stop a probability with which the train departs 1, 2, or 3 minutes earlier") [1]. For each change it combines the arriving train's distribution, the departing train's distribution and DB's transfer time, assuming the minimum transfer time is kept [2][3]. The press reports XGBoost, about 470M training points, a rolling 6-week window and daily retraining [3]. The 38C3 slides list the factors: time of day, train type, distance already travelled, how far ahead the forecast is, and DB's current delay forecast; training data is about 1B stops [4]. The code moved to GitLab [5]; the old GitHub TCP repo is archived [6].
- **Zugfinder:** it has statistics for the last 30 days per train number (older history is paid), arrival tables per station, some timetable routes (Kursbuchstrecken), a check of how safe a change between two trains is, and an AI forecast 3 days ahead (about 79% reliability, per the press) [7][8]. I could not find how the model works.
- **bahn.expert:** the code is no longer public; the repo is only used for issues [9]. I found no evidence of its own delay model.
- **DB Navigator:** it warns when a connection is at risk ("connection will presumably not be reached"), lets you set a longer transfer time, and falls back to historical values when there is no live data [10][11]. I found no public description of a probability model.
- **Academic work on DB data:**
  - Nair et al. (TR-C) combined a random forest (traffic state, weather, events, work zones), a kernel regression per train and a simulation. For about 25,000 trains a day they got +25% forecasts within 1 minute and -50% RMSE compared with the timetable [12]. This is from the abstract only.
  - Consileon's system for DB predicts the change in delay per route section, from current delay and planned running time, and sums the sections [13].
  - The GATv2 paper [14] uses Dutch data, not DB.

## 2. Aggregation by line

I found no service that aggregates by line. Units seen are per stop and run [1], per train number or station [7], per route section [13], and per station or train type [15]. My unverified guess at why: train number plus stop already identifies a line, and delay builds up along the run, so a line average hides the effect of where on the route the stop is [4].

## 3. Transfer times

- **RIS::Stations** (DB API Marketplace) returns transfer times for commuters, occasional travellers and mobility-impaired travellers, and for the station, its surroundings and the city area. Endpoints: `GET /connecting-times/{evaNumber}` and `GET /connecting-times/{fromEva}/{toEva}` [16]. It works per station or station pair. I could not confirm whether it gives times per platform pair.
- **Access to RIS::Stations:** DB must approve you. There is a free test plan (10 requests/s, 10k requests/month); paid plans start at €4,200/year. Data is CC BY 4.0 [16].
- **db-rest (v6.db.transport.rest):** it now runs on db-vendo-client because the old HAFAS API was shut off. `/stops/reachable-from` no longer works and rate limits are lower [17]. `/journeys` only takes a `transferTime` minimum (default 0), plus `walkingSpeed` and walking legs [18][19]. Neither db-rest nor db-vendo-client returns station transfer times or whether a connection is feasible [20].
- I did not check StaDa, FaSta or RIS::Connections in detail.

## 4. Dataset freshness

- The scraper runs 4 times a day against the StaDa and Timetables APIs. Raw data is stored per hour, and a processed monthly release follows [21].
- The HF commit log shows commits every 4 to 6 hours, the latest at 2026-09-12 18:15 UTC. The "Monthly data release for 2026-08" commit landed about 10 days earlier [22].
- The schema changed in February 2026: `train_name` was split, and cancellations became separate arrival and departure fields. `train_line_ride_id` and `train_line_station_num` exist [21].
