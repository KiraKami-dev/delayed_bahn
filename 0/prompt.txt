<result>## 1. Product concept

**error404.ai** is building a Deutsche Bahn journey-reliability predictor for the "Temporal AI" hackathon (EHL Zurich, 12–13 Sep 2026; build started 2026-09-12T12:30Z, submission 2026-09-13T10:00Z per `/Users/akshatkhair/Documents/Projects/temporal_ai_error404.ai/team-setup/state/event.json`). The problem: DB travellers get raw delay data, not a decision — delays *chain* across a journey (train 1 is 5 min late, you still catch train 2, you're now 15 min late, you miss train 3), so "half an hour of buffer" silently fails. The user is a traveller with a multi-leg DB connection. The demo (`team-setup/state/02-demo-script/demo-script.md`): press **Share** in the DB app, share the raw connection text into the team's PWA, the app parses the journey into per-leg cards, a fine-tuned small time-series LLM predicts **each train's delay separately**, chains them into a headline **"Probability your plan fails: NN%"**, and a separate recommendation algorithm gives weather-forecast-style advice ("not 'it will rain' — 'take an umbrella'"), then a proof shot comparing the fine-tuned model against the track-given baseline (raw data pasted into GPT / Claude Opus).

**`Router`** — regex path matching with `:param` segments; only `GET`, `POST`, `DELETE` helpers exist (no `PUT`/`PATCH`/`OPTIONS`):
```js
add(method, pattern, handler) {
  const keys = [];
  const re = new RegExp('^' + pattern.replace(/:(\w+)/g, (_, k) =&gt; { keys.push(k); return '([^/]+)'; }) + '/?$');
  this.routes.push({ method, re, keys, handler });
  return this;
}
get(p, h) {...} post(p, h) {...} delete(p, h) {...}
```
Trailing slash is tolerated (`/?$`). Params are `decodeURIComponent`-ed.

**Handler signature** — every handler is `async ({ params, query, body, req, res }) =&gt; result`. `query` is a live `URLSearchParams` (not a plain object — existing code does `Object.fromEntries(query)` or `query.get('raw')`). Returning a value ⇒ `200` + JSON; returning nothing ⇒ `{}`. If the handler wrote to `res` itself, the framework backs off (`if (res.writableEnded) return;`).

**JSON body parsing** — automatic for non-GET/DELETE, empty body ⇒ `{}`, bad JSON ⇒ `HttpError(400, 'Body must be valid JSON')`. No size limit, no `Content-Type` check.
```js
const body = req.method === 'GET' || req.method === 'DELETE' ? {} : await readJson(req);
```

**`HttpError`** — `new HttpError(status, message, details)`. The catch block uses `err.status ?? 500`, logs 5xx, and replies `{ error: err.message, details: err.details ?? err.body ?? undefined }`. Note: any thrown object with a `.status` property works (the training service does `const e = new Error(...); e.status = 503;`).

## 4. Agents: prediction I/O and CPU paths

`/Users/akshatkhair/Documents/Projects/temporal_ai_error404.ai/app/agents/src/features/db_delay/trip/predict.py`

**Input**: not a journey — it replays *recorded* examples. CLI: `--examples data/trip/examples.parquet` (built by `build.py`), `--checkpoint out/trip/.../checkpoint.pt`, `--start-checkpoint` (default `START_CHECKPOINT` from `model.py`), `--example-ids N [N…]`, `--buffer` (default 8.0 planned minutes), `--min-transfer` (default 5.0), `--device` (**default `"cuda"`**). It looks up rows by `example_id` in the parquet, so it cannot score an arbitrary user-supplied journey today.

**Output JSON** (exact fields, from `summary()`):
```python
{
  "example_id": int, "train": str, "target_stop": str, "planned_arrival": str,
  "headline": f"about +{median} min, likely {low} to {high} min, {on_time:.0%} chance of arriving on time",
  "typical_delay_minutes": int,          # p50
  "likely_range_minutes": [low, high],   # p10, p90
  "p_on_time": round(...,3),             # P(delay &lt; 6 min) * (1 - p_cancel)
  "p_cancelled": round(...,3),
  "rationale": str,                      # prompts.rationale(row), facts read off inputs
  "actual": str                          # ground truth: minutes or "cancelled"
}
```
Top level is `{"forecasts": [...]}`; with exactly two ids it adds:
```python
"change": {"planned_buffer_minutes": float, "min_transfer_minutes": float,
           "p_change_works": round(p,3), "headline": f"{p:.0%} chance of making the change"}
```
Constants: `metrics.LATE_MINUTES = 6` (on-time = delay &lt; 6 min), `LEVELS = 0.05..0.95` step 0.05, `MEDIAN`/`LOW`/`HIGH` = the 0.5 / 0.1 / 0.9 quantile indices.

`connection.py` — pure NumPy, **no torch, no GPU**. `TrainForecast(probs: np.ndarray, p_cancel: float=0.0)`; `change_probability(arriving, departing, planned_buffer, min_transfer) -&gt; float`; `journey_probability(changes: list[(arriving, departing, buffer, min_transfer)], final_arrival=None, arrival_slack=None) -&gt; {"change_probabilities": [...], "plan_success": float, "plan_fail": float}`; and `point(minutes, size=1000, p_cancel=0.0)` — *"A forecast certain of one delay, handy for tests and fixed timetables."* That `point()` + `journey_probability()` pair is your zero-GPU, zero-model path to a real `planFailProbability` from mocked per-leg delays.

**CPU without a GPU:**
- `predict.py --device cpu` is possible (the flag is just passed to `TripTSLM.from_opentslm_checkpoint`), but it loads a Llama-3.2-3B + LoRA checkpoint and needs a `.pt` checkpoint file — none exists in the repo (`out/` is not committed; there is no `data/` either).
- Precedent for CPU inference: `trip/learning_curve.sh` runs `CUDA_VISIBLE_DEVICES= OMP_NUM_THREADS=16 .venv/bin/python trip/train.py --eval-only --device cpu --resume "$dir/checkpoint.pt" ...` — "on the CPU so the training GPU is untouched".
- `trip/baselines.py` is **fully CPU** (`xgboost` `tree_method: "hist"`, `n_jobs: 32`, plus `persistence` and `key history`). But it is a *batch training+scoring* script (`python trip/baselines.py --examples … --out out/trip/baselines`) writing `metrics.json` and `&lt;model&gt;_&lt;split&gt;.npz` of 19 quantiles + `p_cancel` + `p_late`. There is **no single-journey CLI, no saved XGBoost model file, and no exported prediction function usable from the backend**. `persistence()` needs a training frame plus per-row features (`current_delay`, `lead_minutes`, `hist_*`, `station_late_*`, `network_late_*`, …); it cannot run from a share text.

Conclusion for your mock endpoints: nothing today turns a `Journey` into a `Prediction` on CPU. The realistic seam is `connection.py` (`point()` / `TrainForecast` / `journey_probability`) fed with canned or XGBoost-derived per-leg distributions.
